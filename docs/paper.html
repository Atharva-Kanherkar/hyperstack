Abstract. This note surveys recent Y Combinator company engineering openings that emphasize production LLM systems, retrieval, evaluation, multimodal agents, and performance-critical infrastructure (often Python plus Rust, C++, or Go). It summarizes common interview formats at early-stage YC companies, then presents a broad menu of practice projects suitable for deciding a personal learning path. The intent is breadth for selection, not a mandate to complete every item. Compensations and openings change frequently; verify on the linked listings before applying.

1. Demand themes

Across recent batches (approximately W24–S26 / P26), postings that match the stated interests cluster into two overlapping skill families.

1.1 Applied AI product engineering

  • Agent loops, tool schemas, multi-step reliability
  • RAG: chunking, hybrid search, reranking, citation grounding
  • Evaluation harnesses and regression gates in continuous integration
  • Document / OCR pipelines into structured data
  • Context and memory graphs for long-running agents

1.2 Systems × AI infrastructure

  • Rust (or C++ / Go) on the critical path, with Python for ML experimentation
  • Inference operations: batching, KV cache, vLLM / SGLang-class stacks
  • Approximate nearest neighbor / search engines under tight latency budgets
  • GPU orchestration and experiment schedulers
  • Postgres with vectors, or database sandboxes for agents

Pure algorithmic interview drills appear less often than at large product companies. Founders commonly screen for shipping speed, debugging instinct, and the ability to defend engineering trade-offs.

3. Interview process notes

3.1 Common early-stage pattern

  1. Founder or recruiter screen (20–60 minutes).
  2. Technical round: debugging, pairing, ML+coding, or systems deep-dive.
  3. Take-home exercise or a two-to-four hour onsite mini-project.
  4. Team consensus and founder close.
  5. At seed stage, often a paid trial lasting one day to two weeks.

Typical total length is one to three weeks. The decision criterion is closer to “would I want this person shipping with us tomorrow?” than to a multi-bar algorithm screen.

3.2 Company-specific public processes

  • Poly. Intro → insistent project grill → take-home (agent assistance permitted if decisions are defensible) → full team → paid onsite work trial.
  • Thesis. Intro (1h) → coding + ML challenge (90m) → paid one-week in-person trial.
  • PgDog. 30m intro → 1–3h technical deep dive → one-to-two week paid contract → full-time.
  • Zep. Founder screen → two-to-three hour team block (may include a presentation) → decision call.

3.3 Community / candidate signal

Candidate write-ups and hiring-field notes consistently report low LeetCode emphasis at early YC companies relative to large tech firms. Fast loops (“decide within 24 hours”) exist and are themselves a culture signal. A recurring take-home failure mode is over-engineering: for example, building LangGraph + Celery + Redis for a PDF extraction and editable UI task when a simple, correct MVP with a clear “next steps” README would have been stronger. Ask for an hour budget before starting. Where AI assistance is allowed (Poly states this explicitly), expect to defend every implementation choice.

4. Practice catalogue

Each entry is a learning project: study the theory, hand-code the core, use AI for explanation and review (not to write the hard parts), and ship a small artifact that maps to real postings. Identifiers (p1–p24) are for selection in a later syllabus design.

p1. Tool-calling agent from scratch (no LangChain). Demand: very high. Python. 2–3 weeks.
Theory
ReAct, tool schemas, planning vs reactive loops, failure modes.
Hand-code
HTTP LLM client, JSON tool registry, loop with max steps, sandbox tools (fs/http/sql).
AI use
Explain theory; code review; never write the loop for you.

CLI agent + traces + README of tradeoffs.
